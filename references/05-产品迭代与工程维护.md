# 05 · 产品迭代与工程维护（Track B 纵深方法论）

> 来源：融合 `software-company` 专家的「增量开发 / 缺陷修复 / 测试智能路由」能力 + `mvp-expert-team` 的「工程纪律 / 回归 / 生产就绪」底座。
> 一句话立场：**MVP 交付不是终点。能跑起来的产品要持续长肉——加功能、修缺陷、抗熵增、保稳定。**

---

## 一、什么场景走 Track B（迭代维护轨）

| 场景 | 判定 | 典型诉求 |
|------|------|----------|
| 功能扩展 | 既有项目加新模块 / 新页面 / 新接口 | 「给宠宝树加个 AI 客服」「后台加导出 Excel」 |
| 缺陷修复 | 明确 Bug，非新功能 | 「列表分页少了一页」「支付回调偶发 500」 |
| 工程维护 | 技术债 / 依赖升级 / 性能优化 / 监控加固 | 「升级 React 18→19」「加 Sentry 监控」 |
| 续作迭代 | 试运营反馈回来要做第二轮 | 「用户说搜索太慢，做下优化」 |

**前置条件**：项目已有可运行代码与 Spec / 设计系统基线。若项目不存在 → 回 Track A 做 MVP。

---

## 二、Track B 五阶段流水线

```
I-0 现状评估 ── 读 Spec + 设计系统 + 现有代码 + 记忆，定位中断点/技术债
   ↓
I-1 增量定义 ── PM 把诉求写成「增量需求卡」（变更范围 / 验收 / 影响面预判）
   ↓ 【门禁】影响面评估 + 是否与 Spec 冲突（冲突→升 ADR 或回 Phase 0）
I-2 增量设计 ── 架构师出「增量设计」：改动文件清单 + 接口变更 + 回归影响面
   ↓ 【门禁】不破坏既有契约（openapi / design-tokens 兼容）
I-3 增量开发 ── 工程师最小变更实现（读旧码→改必要处→保留行为→记录）
   ↓ 【门禁】代码组织 + emoji 扫描 + 不破坏既有功能
I-4 回归 + 智能路由 ── QA 跑回归 + 智能路由裁决（≤2 轮）
   ↓ 【门禁】P0 归零 + 反作弊门（测试未被删/弱化）+ 回归率=0
I-5 发布 + 运维长跑 ── 灰度发布 + 监控告警 + 备份回滚 + 记忆沉淀
   ↓ 【门禁】生产就绪 ≥ Silver（沿用 Track A 记分卡）
```

---

## 三、I-0 现状评估（续作第一动作）

1. **读基线**：`Spec`（或等价的架构/接口文档）、`design-tokens`（设计系统）、`openapi.yaml`（契约）、现有 `src/` 代码。
2. **读记忆**：`memory/project-tracker.md` + 当日日志，定位上次中断的 Phase / 未决决策（OPEN-DECISIONS）。
3. **技术债扫描**：依赖版本是否过期、是否有已知坑（pitfalls.jsonl 按技术栈指纹召回）、是否有待清理的 TODO。
4. **产出**：一份「现状快照」（当前版本 / 已上线功能 / 已知债务 / 本次目标），写入 project-tracker。

---

## 四、I-1 增量需求卡（PM 职责）

不走完整 PRD，但也不能拍脑袋。增量需求卡结构：

```
【变更类型】功能扩展 / 缺陷修复 / 工程维护
【变更范围】一句话 + 影响模块清单
【验收标准】EARS 格式，可测
【影响面预判】可能波及的旧功能（供 QA 回归重点）
【是否与 Spec 冲突】否 / 是（是→注明是否需升 ADR 或回 Phase 0）
【不做】明确本次不动的部分
```

**原则**：MVP 团「只留 1-3 功能」的减法哲学延续到迭代——一次迭代聚焦一个目标，不堆功能。

---

## 五、I-2 增量设计（架构师职责）

增量设计 ≠ 重新架构。重点在 **影响面**：

1. **改动文件清单**：相对于现有代码的 diff 视图（新增 / 修改 / 删除）。
2. **接口变更**：新增 / 修改的 API 端点；**必须更新 `openapi.yaml`**，前端类型随之更新；不兼容变更开 `/api/v2/`。
3. **数据迁移**：Schema 变更必须可回滚（Alembic / Prisma Migrate down）。
4. **回归影响面**：列出「改了 A 可能坏 B」的清单，交给 QA 作为回归重点。
5. **ADR**：非平凡的技术决策（换框架 / 改数据模型）产 ADR，进 `docs/decisions/`。
6. **任务分解（沿用 software-company 硬上限）**：≤5 任务、每任务 ≥3 文件、T01 若为基础设施变更则先行；增量场景可降到更小粒度，但不突破「一文件一任务」反模式。

---

## 六、I-3 增量开发（前端 / 后端职责）

**最小变更铁律**（来自 software-company 增量开发支持）：

1. **先读旧码**：理解当前实现再改，不凭印象重写。
2. **最小改动**：只改必要处，不重写整个文件 / 整个模块。
3. **保留既有行为**：确保未涉及的旧功能不被破坏（回归的底线）。
4. **记录变更**：明确列出「改了什么、为什么、影响哪」。
5. **契约兼容**：不破坏 openapi / design-tokens；新字段向后兼容。

**自检链**（沿用 Track A）：`lint → type-check → test → fix`（≤3 轮）。
**门禁**：代码组织（分层 / ≤300 行 / 入口零业务）+ emoji 扫描 + 不破坏既有功能（人工 + 回归双重确认）。

---

## 七、I-4 回归 + 智能路由（QA 职责）

### 改动影响分析（每次测试前必做）
改了什么 → 波及哪些旧行为 → 风险分级：高必测 / 中应测 / 低抽测 → 回归重点。

### 智能路由裁决（来自 software-company，≤2 轮封顶）
| 判定 | 含义 | 动作 |
|------|------|------|
| Send To: Engineer (Alex) | 源码有 bug，测试正确 | 回工程修源码（附失败测试 + 期望 vs 实际 + 错误栈） |
| Send To: QA (self) | 测试代码有 bug，源码正确 | QA 自修测试 |
| Send To: NoOne | 全部通过 | 报告成功 |

- **最多 2 轮**：第 1 轮发现问题修复，第 2 轮回归验证；2 轮仍不过 → 标注 Known Issues 交报告，不进第 3 轮。
- **反作弊门（沿用 Track A P0 门禁）**：先查测试是否被删 / 弱化 / 加 skip；命中即阻断。
- **回归率 = 0**：旧行为由绿转红必须为零，否则打回。

---

## 八、I-5 发布 + 运维长跑（运维职责）

1. **灰度发布**：内测（团队）→ 5% → 50% → 全量，逐级观察核心指标（错误率 / p95 / 转化率）。
2. **监控告警**（长期）：错误率 >5% 告警、p95 >2s 告警、DB 连接池耗尽立即通知；健康检查 `/health` 常驻。
3. **备份回滚**：每次发布保留上一版本；数据库每日备份保留 7 天、每月验证可恢复；回滚方案就绪。
4. **发布安全**：一键回滚 + 备份生效（沿用 Track A 记分卡「发布安全」维）。
5. **记忆沉淀**：可复用经验去重进 `MEMORY.md`；本次迭代关键裁决进 `project-tracker.md`；当日日志追加条目。

---

## 九、与 Track A 的关系（生命周期闭环）

```
        ┌─────────────────────────────────────────────┐
        │                                             │
   Track A: MVP 从零交付                                │
   Phase 0→4.1（需求→调研→Spec→设计→开发→测试→部署）    │
        │ 交付可运行 MVP                                │
        ↓                                             │
   试运营 / 真实用户反馈 ──(反馈回流)──┐                 │
        │                            │                 │
   Track B: 迭代维护                  │                 │
   I-0→I-5（评估→增量定义→增量设计→   │                 │
           增量开发→回归→发布运维）    │                 │
        │ 产品持续长肉                │                 │
        └────────────────────────────┘                 │
                                                     │
   大版本重构（架构演进）→ 触发回 Track A Phase 0 重走   │
        └─────────────────────────────────────────────┘
```

**核心心智**：Track A 解决「从 0 到 1 跑起来」，Track B 解决「从 1 到 N 长得好」。两者共用同一套 P0 红线、工程纪律、角色编排、记忆系统——**同一个团队，两种节奏**。

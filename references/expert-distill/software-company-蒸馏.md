## 二、能力边界（擅长 / 不擅长 / 与 MVP 团互补缺口）

### ✅ 此团队擅长（即本次要并入 MVP 团的增量）
1. **快速出可运行代码**：单页应用 / 小游戏 / 工具脚本（≤10 文件）走「快速模式」，跳过 PRD/架构，工程师一次性写完，QA 验证即交付。
2. **增量开发（持续迭代核心）**：接收既有代码的变更请求时——先读旧码理解实现 → 最小变更（只改必要处，不重写整文件）→ 保留既有行为 → 记录变更原因。这正是 MVP 团「不做存量重构/长期演进」的缺口。
3. **标准化任务分解**：≤5 任务硬上限、每任务 ≥3 相关文件、按功能模块分组、T01 必为基础设施（配置+入口+依赖声明）。防止 AI 过度按单文件拆任务。
4. **测试智能路由**：每轮测试后做路由裁决 —— 源码 bug 回工程、测试 bug 自修、全过则 NoOne；**最多 2 轮**（非 5 轮），控制交付节奏。
5. **部分工作流**：仅 PRD / 仅架构评审 / 仅代码实现 / 仅测试 / 仅市场调研，灵活适配「用户只要某一段」的诉求。
6. **工作流路由判断**：按规模自动选 快速 / BugFix / 标准 SOP / 部分，宁轻勿重。

### ❌ 此团队不擅长 / 与 MVP 团互补的缺口
1. **无 UI 设计师角色** → 无专业视觉、设计系统、反 AI 模板（emoji/紫粉渐变/模板味三红线）。MVP 团设计师补。
2. **无运维 / 部署角色** → 标准 SOP 止于测试，无部署验证、回滚、监控告警。MVP 团运维补。
3. **无「原型验证」专项** → 无 EARS 验收标准、openapi.yaml 机器契约、design-tokens.json。MVP 团 Spec/设计细化阶段补。
4. **交付即止** → 无「试运营 → 反馈 → 迭代 → 维护」生命周期闭环；迭代/维护能力本次融合补齐。
5. **默认栈偏前端 SPA**（Vite+React+MUI+Tailwind），后端仅 "if applicable"；缺多端 / 小程序 / 云原生选型矩阵。MVP 团架构师选型包（A-D）补。

## 四、去重说明

- **重叠部分（以 MVP 团更深版本为准，不重复建设）**：PM 竞品分析、架构师分层架构、工程师分层代码、QA 测试金字塔 —— software-company 在这些维度较浅，直接复用 MVP 团 7 角色已有方法论。
- **不新增角色**：software-company 的 PM/架构/工程/QA 与 MVP 团的 PM/架构/前端/后端/QA 职责同构，融合后 **不新建重复角色**，仅在 MVP 团 7 角色上「叠加增量开发 / 迭代维护」职责，并保留 MVP 团独有的 UI 设计师与运维工程师。
- **融合后角色总数**：仍为 7（PM / 架构 / 设计 / 前端 / 后端 / QA / 运维），但每位都具备「MVP 从零」与「迭代维护」双重能力。

## 五、蒸馏结论

software-company 的本质价值不是「又一套团队」，而是给 MVP 团补上 **「交付不是终点」** 这一环：把一次性 MVP 交付扩展为 **MVP 快速验证 → 试运营 → 持续迭代 → 工程维护** 的产品生命周期。其任务分解上限、增量开发纪律、测试智能路由三项是最高价值增量，已并入统一复合团队定义（见 SKILL.md Track B 与 references/05-产品迭代与工程维护.md）。
